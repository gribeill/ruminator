# ruminator development plan

The project will generate a minimal, distraction-free daily arXiv browsing page, initially focused on `quant-ph`. It should feature six papers, preserve access to the full posting list, and encourage serendipitous discovery rather than replace reading papers. Ranking should use a small semantic pipeline; LLM summaries for featured papers should be provider-independent and cached to limit token spend.

## Scope and architecture

The local-first implementation is complete: TypeScript, SQLite, manual generation, and a small local reading/voting server. The next phase makes the hosted application authoritative for the admin and invited users' daily use, while preserving independent fully local runs for testing and people who prefer or require a non-hosted installation. Keep APIs flat and explicit; prioritize correctness and readable code over infrastructure. The hosted contract below supersedes earlier deferrals of Cloudflare integration and scheduling. Hosted feasibility has been established and its experimental code retired; the local hosted auth/reading slice exists, but the complete production service is still planned and has not been deployed.

### Current deployment scope: disposable hobby installation

This is WIP/development software. Breaking changes are welcome; optimize for clarity, safety and low cost, not production-grade continuity. Roughly daily weekday execution and **~90% availability (a single nine)** are sufficient; this is a tolerance, not a monitored SLA. Missed updates, downtime, safe large-paper failures and manual repair are acceptable. Keep the previous publication readable when available, but do not add failover, watchdogs, recovery services, migration tooling or paid monitoring to chase uptime.

The user has approved discarding **all existing hosted application state**, including accounts, interests, configuration, votes, publications, caches and generation records. Use an explicitly confirmed clean D1 reset/recreation and the current schema, not a preservation/migration project. No backup/export or proof of empty tables is required. Confirm the exact remote resource/commands and quiesce old execution before erasing claims; a reset must not enable duplicate paid effects. Re-provision the verified admin and reviewed configuration afterward. Standalone local state is outside this permission, and future retained user data needs a fresh decision. Historical preservation requirements below and in `hosted.md` are superseded for this deployment.

The estimated project budget is **~$5/month, a soft target rather than a hard ceiling**. Existing token estimation/per-user limits plus Cloudflare's configured daily and monthly spending caps are sufficient cost controls. Review prices, included allowances, fixed charges and any external-provider costs outside those caps with a rough monthly estimate, not exact cost attribution. Start owner-only and check usage after the initial run and periodically or when expanding. Pricing/tokenization uncertainty and cap enforcement lag/in-flight spending are accepted; no exact maximum bill is promised. Do not add an internal dollar ledger, aggregate monthly budget service or a deployment requirement to prove every charge fits $5. Keep durable no-repeat claims and reservations; accept skipped runs when configured caps are reached.

Low availability does **not** relax verified authentication, invitation/role/ownership boundaries, CSRF/Origin/stale-form checks, private no-store responses, secrets handling, bounded inputs, atomic publication or durable no-repeat claims and reservations. Keep existing per-user budgets and verify upstream retry/fallback behavior. Use representative deployed checks and a large-paper case, not load testing or an availability programme. See [the deployment checklist](../hosted-readiness.md). Remote reset/deployment and paid activation remain separately confirmed operations; this plan update performs none.

Separate these responsibilities:

- **Ingestion:** fetch arXiv announcement batches and cache paper metadata.
- **Generation:** read profiles and a snapshot of feedback, obtain embeddings, compute scores and selections, request summaries, and save a completed digest.
- **Presentation:** render saved digests as static HTML. Browsing does not call models or recompute rankings.
- **Feedback:** persist explicit votes for use in subsequent digests; hosted writes require authentication and authorization for the affected user's data or the admin-only operation, while the local server remains available for standalone use.

Use narrow provider-independent interfaces for embeddings and summaries. Use BGE-small-en-v1.5 as the initial embedding model, locally through Transformers.js/ONNX. It produces 384-dimensional vectors and has a 512-token context window. Its availability in Cloudflare Workers AI (`@cf/baai/bge-small-en-v1.5`) provides the initial hosted candidate, subject to checking its API, limits, and preprocessing before implementation. Record provider/model identity and content hashes in caches; vectors from incompatible models must not be compared.

Use two SQLite databases and a small database module, keeping SQL within D1's supported SQLite subset where practical. Keep downloaded paper information/source metadata separate from disposable application state. Use current schema definitions only: no migration runner, version upgrades, or legacy schema fallbacks during development. Isolate filesystem, local-server, and database-driver dependencies from ranking and generation logic. For hosted operation, introduce only the narrow D1 access needed by the application; do not build a generic storage framework. Preserve SQLite support for standalone local operation.

### Ephemeral listing contract (supersedes historical retention below)

For each standalone local installation, keep one global published listing and at most one resumable working listing, not an archive per date/category combination. Hosted operation extends this to one publication and at most one working generation per user; only the admin's publication is public. Shared caches must retain inputs still needed by any user's current/working listing or active feedback. Manual `generate` fetches and ranks; `generate --summarize` additionally retrieves featured text and makes explicitly authorized paid calls. These manual authorization rules continue to apply to local commands; hosted scheduling and its explicit summary authorization are described below. A repeated published batch is a no-op; `generate --clear` resets only listing-generation state and regenerates, preserving the old publication until replacement and requiring `--summarize` again for paid calls. Individual development commands remain available.

Publish atomically only after ranking (and requested summary attempts) completes. Missing HTML/API summaries do not block publication; feed/ranking failures leave the previous listing readable. The server follows replacements without inference. Prune superseded batches, rankings, full text, summaries, run snapshots, and unneeded embeddings. Keep only latest active votes, expiring 365 days after their last explicit change; using feedback does not renew it. Keep voted metadata for re-embedding and current/staging inputs, plus model assets. Prune during generation, whether manually or scheduler initiated. No historical navigation or archive reconstruction. Schemas may break during development; no compatibility or migration layer.

### Daily lifecycle and immutability

1. Fetch a posting batch and snapshot the profiles, configuration, and votes available at generation start.
2. Generate and persist scores, selections, summaries, and the complete remaining-paper order.
3. Atomically publish the completed digest to the hosted or local reading view.
4. Store subsequent votes separately; they affect only future digests.

The current ranked listing is stable: page refreshes, new votes, and provider/configuration changes do not reorder it. Fetch-only/unranked work stays in staging, invisible to the reading server. Cache intermediate work so interrupted generation resumes without repeating paid attempts. Atomically replace publication only after ranking and any requested summary attempts finish, then prune superseded artifacts. `generate --clear` explicitly restarts working generation while preserving the old publication until replacement. Seeded randomness is reproducible, but persisted order guarantees display stability.

### Research-interest configuration

Use one `interests.md` file containing six independent profiles. Each `## Display name {#stable-id}` heading starts a profile; `### Subjects`, `### Keywords`, and feedback/example headings belong to that profile. Explicit IDs preserve existing identities and stay stable through heading renames/reordering. Parse profiles in ID order so file arrangement does not alter tie-breaking. Subjects remain the only semantic content besides display names; keyword groups remain separate lexical inputs. Missing keywords stay neutral. `--profiles` accepts a Markdown file path, not a directory. There is no parallel/legacy directory format.

### Local storage

- **`data/papers.sqlite`** (`schema/papers.sql`): current per-category downloads/freshness and current/working paper metadata/HTML. Not a historical archive.
- **`data/app.sqlite`** (`schema/app.sql`): one publication, one working generation, needed embeddings, active vote memory, and current generation/summary provenance. Recreate explicitly for incompatible schema changes; no migration runner.
- **`data/models/`**: independently cached model assets, also preserved during application DB resets.

Expose separate `--papers-db` and `--app-db` paths; reject the same file including aliases. Offline generation uses only current downloaded category feeds and cached models; reject mixed dates rather than finding an older shared batch. `serve` displays only the current publication, follows replacements on refresh, and never reconstructs history or invokes a model.

Retain at least:

- Papers: arXiv ID/version, title, abstract, categories, and source metadata.
- Posting batches: announcement date and paper membership, separate from paper identity.
- Profiles and embeddings: content/configuration snapshots or hashes, model identity, and vectors for papers and profile inputs.
- Votes: latest active paper identity, up/down value, metadata, and explicit-change timestamp. Compact superseded/cleared events and expire votes older than 365 days during generation; feedback use does not renew retention. Remove expired metadata from frozen provenance too, without changing scores/order.
- Generation runs/digests: posting batch, configuration/profile/model identities, feedback snapshot, completion state, ordered paper membership, and selection roles.
- Scores: semantic, keyword, feedback, and combined relevance components for inspection.
- Summaries: structured response and cache identity.

### Hosted authority and personal-site integration (next phase)

The online installation is the authoritative source for the admin and invited users' listings, interests, votes, retained paper metadata, embeddings, and generation/summary state. It must generate and serve independently of the admin's computer. Invite-only multi-user operation supersedes the earlier owner-only hosted design; standalone local behavior remains unchanged. Standalone local installations remain supported, using their own SQLite state and local embeddings; they are not synchronized replicas or a prerequisite for hosted generation.

Integrate at a subdomain such as `papers.ribeill.net`. The personal website currently builds Hugo/XMin and serves its generated assets through Cloudflare Workers. Prefer a separate ruminator Worker, linked from the main site and visually consistent with it, so paper publication does not require a Hugo rebuild. Hugo export and cross-repository publishing are not prerequisites.

#### Invite-only accounts, public reading, and private feedback

- The admin's current sorted listing, abstracts, and available summaries are publicly readable without login. The public view excludes private vote states. Public page requests never fetch papers, invoke models, or start generation.
- Admission is invite-only, initially for a handful of friends. Each invited user has a private personalized listing, their own `interests.md` document, and independent votes. Users may read and vote on their own listing and edit their own interests; they cannot trigger rescoring, pipeline runs, summary requests, or resets. There is no open registration or user-publication feature in this phase.
- Agreed boundary: public `/` and KaTeX assets; authenticated `/reader` (including `/reader/vote`) and `/interests`; admin-only `/admin/*`. Use Cloudflare Access emailed one-time codes with seven-day sessions. Maintain invited emails manually in Access, the sole invitation list. Automatically provision approved identities on first login as regular users with stable application IDs, keyed by verified issuer/subject; never take ownership or roles from submitted fields. Provision the sole admin role explicitly in D1, outside editable TOML.
- New users receive the agreed six-profile, broad quantum-computing default interests (qubit hardware; control/measurement; error correction; algorithms; architecture/scaling; simulation/applications). The valid default makes them eligible for the next scheduled update without an initial edit. Editing/saving applies only to the next run and never invokes inference; before first publication show a waiting message, never another user's private listing. Default onboarding supersedes the earlier suggestion to require an initial save.
- Check the D1 enabled flag on every private request and in mutation predicates. Removing an invitation alone is not immediate revocation of an existing JWT: disable the application user, remove Access admission, and revoke sessions. Logout uses Access's logout endpoint, not a new application session system. Keep invitation/role management manual initially; later editors should reject conflicting saves while preserving submitted text.
- Enforce identity, role, and per-user ownership server-side on every private page and mutation endpoint. Validate Access assertions if using Access; do not trust unverified identity headers or hidden controls. Retain CSRF/Origin checks and user/publication-bound stale-form rejection. Knowing another user's listing ID must grant no access.
- Keep other users' listings, interests, votes, authentication material, and administrative state out of public responses and public caches. Private responses must not leak across users. Secrets stay in hosted secret configuration, never in editable TOML, published artifacts, or snapshots.

#### Plain-text editing and explicit admin actions

- Provide a plain Markdown editor for each user's interests, including the admin's. Preserve the existing profile syntax and stable IDs; validate before saving and display errors without discarding the edited text. Avoid a new profile-building abstraction.
- Provide the admin a plain-text TOML editor for hosted `config.toml` settings, validated before saving. Regular users cannot change configuration or budgets; credentials are not editable through this interface.
- Saving interests or configuration never scores papers, retrieves text, calls a model, or changes an existing publication. Show that changes are pending for the next run, with enough saved/applied state to distinguish the editor contents from the current listing's frozen inputs.
- Interests apply on that user's next scheduled run. Global configuration changes apply on each user's next update, without retroactively rewriting existing listings or mutating an in-progress snapshot. Regular users cannot force an update after saving; unchanged batches remain no-ops unless an admin explicitly rebuilds their own listing.
- Separate **Save**, **Rebuild ranking**, and **Regenerate summaries** actions. Only the admin can clear their daily scores/summaries or rerun the pipeline, and these actions affect only the admin's listing and its public view—not other users' published or working state. Make the affected scope and potential paid calls explicit before execution; clearing alone is not authorization for paid regeneration.
- Admin rebuilding uses the current published posting batch and latest saved admin interests/configuration, preserving the old publication until replacement is ready. Summary regeneration is a bulk action for all six featured summaries, not per-paper selection: preserve ranking/order and its inputs while freezing the latest saved summary settings. Both require explicit paid-call confirmation and reject unfinished admin work; no cancellation/takeover. Regeneration is an explicit exception to no-retry policy in a new generation, never a reset of other users' claims, budgets, or saved summary text.

#### Weekday generation and execution

- **Right-size for a small daily reader.** This serves a small invited group, mostly once per weekday, not a high-availability job platform. Prioritize low operating cost, readable code, and safe paid effects over automatic recovery or guaranteed completion time. Retain frozen inputs, atomic publication, durable no-repeat claims, per-user budgets, shared caches, and one working generation per user. Occasional failed or missed runs are acceptable when the previous publication remains readable.
- **Minimal orchestration only.** Wire the existing runner into one Workflow per generation, with sequential bounded steps and the same persisted generation ID across retries. Reuse existing lifecycle, claim, and budget records. Add storage or coordination only where a concrete duplicate-delivery/replay test demonstrates a gap. Do not add leases, automatic claim takeovers, a generic job framework, a second lifecycle state machine, continuous watchdogs, or elaborate stranded-launch/recovery machinery. Prefer next-boundary failure or explicit operator intervention for rare failures.

- Target one hosted run around **06:00 America/New_York, Monday through Friday**, observing Eastern daylight saving time. The date shown remains the arXiv announcement date, not the scheduler date. Holidays or unchanged feeds may produce no new listing.
- Agreed scheduled policy: request all six featured summaries (or fewer for small batches) for every enabled user, within independent frozen per-user limits. Fetch the configured category feeds once for the cohort. Any fetch/parse failure or mixed-date batch skips generation for everyone that day, preserving publications; a valid feed with no new papers is not a failure. Duplicate or interrupted passes do not automatically retry ingestion/admission.
- Cloudflare cron schedules use UTC; design a timezone-aware gate or equivalent scheduling strategy rather than treating Eastern time as a fixed UTC offset. Deduplicate by intended local run date, user, and batch, and prevent conflicting scheduled/admin generation for the same user. Shared inference/cache writes also require concurrency-safe claims.
- Use one Cloudflare Workflow per user generation, with D1 authoritative for admission, claims, frozen inputs, deadlines, and publication. The account is Workers Paid with Workers AI enabled. Closing a private page must not interrupt generation. Local probe C established replay-safe feasibility; deployed CPU/memory/resource behavior remains unverified. Persist small IDs/results in Workflow steps, not full text or digests; the journal is not long-lived application storage.
- At the next scheduled weekday 06:00 Eastern boundary, mark an unfinished prior generation failed, retain its last publication and spent/ambiguous claims, and admit the latest batch. Atomically fence the old generation from new claims and publication; already-admitted/in-flight requests cannot be unsent. Keep fresh activity checks before external effects/persistence, without claiming an atomic transaction between D1 and an external provider. Admin resets remain scoped to the admin's generation.
- The scheduled run updates each invited user's private listing and the admin's public/private listing from their respective interests and votes. Share ingestion and compatible inference work where possible; one user's failure must not invalidate another user's completed publication.
- Preserve per-user generation-start profile/configuration/vote snapshots, cached progress, sequential featured-summary requests, durable pre-request claims/budget reservations, and no automatic retry of actual summary attempts. Acquire/check the durable claim inside the retried effect callback itself; never trust a cached step result saying it previously won admission. Retry result persistence without repeating the provider call while its response is available; otherwise finalize an ambiguous attempt as unavailable without refund or lease reclaim. Do not finalize another user's in-flight shared claim. Execution-platform retries must not repeat admitted paid effects; Gateway/provider retries and fallbacks must be independently disabled/verified before summary deployment.
- Hosted scheduled summaries require explicit admin-enabled configuration and budgets before activation; an enabled schedule is standing authorization within those limits, not permission granted by visiting or editing a page. Token budgets in `config.toml` apply per user, not as one shared run allowance. Retain visible failure/skip states and admin-only reset/rebuild controls scoped to the admin's listing. No live model calls, paid smoke tests, or schedules are activated merely by updating this plan.
- Keep the current publication readable during work and after failures. Publish atomically only after ranking and requested summary attempts finish. A repeated published batch is a no-op; scheduler delivery is not permission to clear or rerank it.

- Use **D1** for user identities/roles, saved interests and admin configuration, each user's current listing and resumable staging, the day's text, and long-lived metadata needed for active feedback and inference. - Share ranking, selection, extraction, summary policy, and rendering logic where practical. Isolate Workers/D1/inference dependencies from local filesystem, SQLite-driver, and local-server dependencies with minimal explicit interfaces.

## Retained hosted feasibility findings

Probes A/B/C established the architecture and have been removed along with their experimental schemas, Workers, tests, synthetic tokenizer, and live smoke command. These are design findings, not a production generation adapter or deployment authorization:

- **Runtime:** shared RSS/HTML parsing, Markdown/TOML validation, token counting, and KaTeX rendering worked in local workerd without Node compatibility. Keep the platform-neutral modules used by the application. Local timings and bundle acceptance are not hosted CPU/memory guarantees.
- **D1:** use one transaction domain with logically separate source/application tables, normalized immutable membership/content, and atomic per-user publication/accounting. Store large text as UTF-8 byte chunks of 256 KiB, read/write at most eight chunks per page/batch, and verify completion, length, and SHA-256 before use. D1's documented row/value limit is 2,000,000 bytes; statements are limited to 100,000 bytes/100 bound parameters and results to 50 MB. Recheck [current D1 limits](https://developers.cloudflare.com/d1/platform/limits/) when implementing. Sessions provide sequential consistency, not multi-query snapshot transactions; cleanup must preserve immutable artifacts held by in-flight readers.
- **Execution:** one Workflow per user generation, with D1 authoritative for admission, claims, deadlines, and publication. Claims/reservations belong inside the retried effect callback; ambiguous paid calls remain charged and are never automatically resent. Retry only result persistence while the response remains in memory. Do not finalize another user's shared claim. Pass small references through the journal, not full texts/vectors; the reviewed non-stream step-result limit was 1 MiB. Recheck [Workflows limits](https://developers.cloudflare.com/workflows/reference/limits/) before deployment.
- **Hosted BGE:** Workers AI `@cf/baai/bge-small-en-v1.5`, 384 dimensions, explicit `cls` rather than the API's default `mean`. Count CLS/SEP within the 512-token limit, repeat the title across sentence/token-bounded chunks, apply the retrieval instruction to profiles only, L2-normalize chunks, average, then renormalize. Keep its fingerprint separate from local ONNX, including provider/model/pooling/tokenizer/preprocessing/aggregation and an application invalidation epoch. No pinned provider weights or deployed tokenizer are exposed.
- **Tokenizer metadata:** standalone `@huggingface/tokenizers` 0.2.0 was verified with `BAAI/bge-small-en-v1.5` revision `5c38ec7c405ec4b44b94cc5a9bb96e735b38267a`. `tokenizer.json` SHA-256: `d241a60d5e8f04cc1b2b3e9ef7a4921b27bf526d9f6050ab90f9267a1f9e5c66`; `tokenizer_config.json` SHA-256: `9261e7d79b44c8195c1cada2b453e55b00aeb81e907a6664974b4d7776172ab3`. Package verified metadata for hosted execution; do not depend on a personal model cache or a moving upstream revision.
- **Authorized live result:** one five-input Workers AI batch returned five 384-dimensional CLS vectors with local token counts `[512, 512, 260, 24, 512]`, no retries or summaries. This verifies endpoint/shape acceptance, not tokenizer equivalence, stable weights, or ranking quality.
- **Remaining deployment checks:** production schema/retention and artifact packaging, deployed admission/deadline fences, Gateway single-attempt/no-fallback settings, deployment permissions, and hosted resource behavior. Local bounded shared waiting is implemented; stranded launches intentionally await intervention/the next boundary, not a reconciliation service. No schedule or further paid call is authorized by the completed experiments.

## Agreed ranking and browsing design

### Local embedding baseline

- Embed each paper's title and abstract as scientific source text, not rendered HTML.
- Build profile queries from the profile name and positive subjects; exclude Keywords, comments, empty sections, and negative feedback. Apply BGE's recommended retrieval-query instruction to profiles, not papers.
- Use model-appropriate pooling and L2 normalization. Split overlength paper inputs into sentence-oriented, token-bounded chunks with the title repeated; average chunk vectors and renormalize rather than silently truncating long abstracts. Account for special tokens and the title within the context budget.
- Use maximum cosine similarity across profiles for the initial raw semantic score; retain all per-profile similarities for inspection. Display `(cosine + 1) / 2` on a fixed [0, 1] scale, rounded to three decimals, with the closest profile in a tooltip. This normalized semantic component feeds the combined relevance score; the visible number is now the combined score.
- Download model assets once into a repository-local ignored cache, then support offline inference. Cache vectors by content and a fingerprint including model revision, backend, precision, pooling, and preprocessing/chunking configuration.
- Implemented artifact: `Xenova/bge-small-en-v1.5`, revision `ea104dacec62c0de699686887e3f920caeb4f3e3`, q8 CPU inference through pinned Transformers.js 4.3.2. Model assets live under ignored `data/models/`; vectors and score snapshots live in SQLite. `score` processes saved data without arXiv calls; `--offline` also prohibits model downloads. `start` scores new/unscored digests; `serve` never performs inference.
- Semantic snapshots retain the original profile inputs; the first complete ranking replaces a provisional random preview with persisted selections/order. Once ranked, profile/model/configuration changes affect future digests only. Preserve the complete profile inputs and model fingerprint with each score snapshot.
- Treat local ONNX and future hosted outputs as distinct embedding spaces until compatibility is verified; sharing a model name does not guarantee identical preprocessing or vectors.
- Inspect scores on real cached postings and evaluate a small set of reader-labeled matches, adjacent papers, and misses before calibrating combined scoring. Cosine similarity is not a probability; avoid daily min-max normalization that forces a weak day's best match to appear maximally relevant.

### Relevance

Start with `S = 0.60 * semantic + 0.25 * keywords + 0.15 * feedback`, with components normalized to comparable scales. These are initial weights, not calibrated constants.

Explicit up/down votes mean more or less relevant to the reader's interests, not judgments of scientific quality. Feedback should inform relevance for future papers; absent evidence should be neutral. Vote feedback uses raw paper-embedding cosine similarity with configurable cutoffs (`[feedback]`): minimum similarity 0.90, near-duplicate similarity 0.95. For each new paper, consider nearby active voted examples newest first and greedily discard examples duplicating an already retained base ID or near-duplicate vector. Latest votes win conflicts among duplicate examples. Weight retained evidence as `(cosine - cutoff) / (1 - cutoff)` and compute `feedback = 0.5 + 0.5 * sum(weight * signed_vote) / (1 + sum(weight))`. This neutral pseudocount keeps weak/sparse evidence conservative; no evidence stays 0.5. These are uncalibrated defaults, not a learned probability. The generation-start snapshot freezes active votes and thresholds through resumption; cached embeddings must match the generation model fingerprint. Persist full input/model/vector provenance for inspection without displaying it on the reading page.

Keyword matching uses only explicit `### Keywords` bullets. Semicolons separate aliases in one group. Match whole phrases after case/punctuation/hyphen/simple-plural normalization, never partial coverage or inferred Subjects words; respect even broad terms if explicitly configured. Count each alias group at most once, weight title hits 2× abstract hits, and saturate as `1 - exp(-evidence / 2)`. An absent/empty list is neutral 0.5 for that profile; a configured list without hits scores 0. Take the strongest profile, including neutral values (an unspecified profile gives a 0.5 floor). Persist keyword lists separately with each ranking, alongside matched groups and all score components. Keyword-only edits do not change embedding inputs; when resuming a semantic-only stage, retain frozen semantic inputs but use the current explicit keyword lists for its first ranking. Published rankings remain fixed. Scores are not probabilities or scientific-importance estimates.

### Featured papers

Show titles, LLM-generated summaries, and abstracts for six distinct papers:

1. Four highest relevance scores, with a small redundancy penalty.
2. One adjacent-topic paper: favor semantic connections with low keyword overlap and a topic not already represented.
3. One wildcard: a date-seeded random draw from remaining candidates, excluding near-duplicates of the other selections.

Implemented defaults in `src/ranking.ts`: top-slot redundancy penalty 0.04; adjacent score = semantic − 0.35 × keywords − 0.15 × maximum featured similarity + 0.05 for an unrepresented best-matching profile. Avoid identical titles and cosine similarity ≥0.95 for featured slots when alternatives exist. If a pool is too small/redundant, relax that preference to retain up to six distinct IDs; allocate relevance slots first, then adjacent, then wildcard.

For the wildcard, use an equal mixture of uniform sampling and softmax sampling over semantic relevance (initial temperature 0.05, chosen after inspecting the observed semantic range of approximately 0.808–0.903). Feedback may later make a modest adjustment; keywords and hard relevance cutoffs should not constrain this slot. Calibrate softmax temperature against observed similarity distributions rather than assuming a scale.

### Featured-paper summaries

Summarization runs strictly after scoring and saving the six featured selections. Summary availability, extraction failures, and token budgets must never change semantic scores, relevance, selections, or display order. Only featured papers are eligible; each uncached paper gets a separate request, sequentially in saved featured order, never a batched request.

Acquire full text only from versioned arXiv HTML for now. TeX source and PDF extraction are deferred until HTML coverage proves insufficient. Cache raw HTML, extracted text/hash/provenance, and unavailable states by paper ID/version in the paper database; cached raw HTML supports local re-extraction without another download. Require explicit retries for unavailable results. Never execute scripts or fetch page assets. If HTML is unavailable or unusable, mark the paper unsummarized. Do not silently substitute abstract-only input or truncate a paper. `text` is an explicit retrieval command; scoring, serving, and ranking do not acquire full text.

Request a short two-sentence factual summary covering the scientific question, what was actually done, and the principal result or qualification. Ground it in the supplied full text, preserve uncertainty, distinguish proposals, simulations, proofs, and experiments, and do not invent findings or judge scientific quality. Treat paper text as data, not instructions. For this first version, retain only the summary, not an evidence schema, result taxonomy, or personalized relevance reason.

Use a small provider-independent interface, initially accessed through Cloudflare AI Gateway with explicit configurable provider/model selection (Workers AI or an external vendor). Scientific summaries do not depend on profile context or selection role. Validate nonempty textual output before caching; do not cache errors as successful summaries. Preserve published summary text rather than rewriting it when configuration changes. The first explicit summary command adds outcomes to an existing ranked digest; each recorded attempt/budget outcome then stays fixed unless the user explicitly invokes `summarize --clear`; HTML-unavailable preconditions can be rechecked on a manual rerun. Page requests never acquire text or invoke a model.

## Implemented source and batch semantics

Use `https://rss.arxiv.org/rss/{category}`, which includes abstracts and the current announcement batch without per-paper scraping or pagination. Include `new` and `cross` announcements, exclude `replace` and `replace-cross`, and deduplicate papers across configured categories. Derive the announcement date from channel `pubDate` in US Eastern time, not the local calendar date or a submission-date search. Display the reported date; the latest batch can predate today, especially around weekends/holidays. There is no historical backfill yet.

Require all requested feeds to report the same date. Keep successful current-category downloads independently, but publish only complete ranked listings. Each category retains its current source batch, not older batches. Repeated published batches are no-ops; explicit `generate --clear` rebuilds from the current download cache (or a fresh download with `--refresh`). There is one global publication across category combinations.

The local server binds only to loopback and serves the current publication without network access on page requests. It follows replacements on refresh and rotates form tokens to reject stale votes, including after a same-batch clear/rebuild. Math is rendered server-side with KaTeX for `$…$`, `$$…$$`, `\(…\)`, and `\[…\]`; styles and fonts are local assets, so cached reading needs neither a CDN nor client-side scripts. Paper HTML remains escaped and KaTeX trust features are disabled; unsupported math falls back to escaped source.

A separate per-category download cache tracks when feeds were successfully retrieved, independently of announcement dates and immutable published digests. `start` and `fetch` reuse downloads from the current US Eastern calendar day, even across different category combinations. `--refresh` explicitly bypasses this cache, without overwriting published digests. The bounded current download cache lives in the paper database and can support offline generation after application resets; there is no historical archive. Failed requests do not advance cache freshness, while successful categories remain cached if a later category fails. Since the cache checks only once per calendar day, a later same-day feed update requires an explicit refresh. `start` reports download failures rather than silently serving stale data; `serve` explicitly opens existing data offline.
