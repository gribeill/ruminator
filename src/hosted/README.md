# Hosted entry point

See [the hosted guide](../../hosted.md) for preview commands, the security boundary, limitations, and deployment prerequisites.

- `workflow-limits.ts`: four embedding requests/one summary request per ten-minute callback, leaving one minute beyond worst-case transport timeouts; per-request input batches are unchanged.
- `worker.ts`: HTTP entry, gated scheduled handler and exported `GenerationWorkflow`. Production enables confirmed admin actions and the authorized weekday 06:00 America/New_York schedule with the approved Workflow binding. Cron `0 10,11 * * MON-FRI` supplies both DST candidates; the intended-time gate admits only Eastern 06:00. Local preview keeps execution off.
- `activation.ts`, `execution.ts`, `production-workflow.ts`: deployment-only activation/credential preflight and production adapter composition over the existing runner; no new job lifecycle or schema.
- `html-source.ts`: bounded, credential-free, versioned arXiv HTML retrieval/re-extraction; no redirects, PDF fallback or retries.
- `app.ts`: explicit routes, response/cache policy, and reading controls. Vote POSTs keep native redirects by default, returning private/no-store JSON only for an explicit `Accept: application/json`.
- `assets/votes.js`: hosted-only progressive vote enhancement, packaged with KaTeX by `scripts/hosted-assets.ts`. Updates only confirmed state, disables the affected paper while saving, reports failures inline, and never retries/resubmits automatically. Public/local readers remain script-free.
- `auth.ts`: Access JWT/JWKS validation and session/scope-bound CSRF forms.
- `editors.ts`: native interests/configuration forms, conflict preservation, and saved/applied ranking/summary revision status.
- `populate-feed.ts`: admin-only, cohort paid-confirmation form that works before first publication; session/action/date/configuration/pass-bound tokens and atomic attempt IDs prevent replay. Fetches once, then launches independent per-user Workflows; already published batches are no-ops and unfinished work is never replaced.
- `admin-controls.ts`: separate paid-confirmation forms for own-listing rebuild/bulk featured-summary regeneration; requires an explicit execution switch, valid credentials and Workflow binding, rejects unfinished work, and consumes stale/replayed forms through the existing latest-run record.
- Summary execution reuses its frozen/verified context for cache lookup; `readExtractedText` verifies text without materializing raw HTML. Fresh owner/pin/effect SQL checks remain in place.
- `summary-regeneration.ts`: reuse the published ranking and private feedback provenance without embedding/reranking; publication verifies unchanged ranking rows.
- `saved-inputs.ts`: validated, revision-checked D1 document reads/saves.
- `reading-store.ts`: minimal D1 accounts/reading/vote queries; generation storage modules remain internal, not execution endpoints.
- `default-interests.ts`: public starter document used only when provisioning new users.
- `bge.ts`, `assets/bge/`: hosted-only CLS adapter and verified packaged tokenizer metadata; no weights or runtime downloads.
- `embedding-requests.ts`: durable effect admission, completed chunk reuse, and fail-without-resend handling.
- `ranking-runner.ts`: bounded ranking-only or explicitly requested ranking-plus-summary execution from frozen inputs; adapter setup receives only IDs/intent, and the summary phase reuses the loaded snapshot. Retention runs at admission and successful publication, not on every continuation. Execution is admitted separately from reading/editor requests.
- `daily-runs.ts`: once-per-intended-Eastern-date admission, stable generation/Workflow IDs, and next-weekday-boundary failure (including disabled owners); no trigger or launch-recovery service. `prepareDailyRunStep` explicitly performs lifecycle maintenance before checking eligibility.
- `generation-lifecycle.ts`: one atomic failure transaction, with distinct enabled-owner and trusted daily-reservation authorization.
- `generation-inputs.ts`: frozen snapshots and explicit captured/unchanged/blocked daily admission results. Manual snapshots also record action/base publication and, for summary-only work, a separate frozen summary configuration.
- `generation-workflow.ts`: sequential bounded steps around the existing runner, reference-only journal, and three bounded shared-work sleeps; adapters are explicitly supplied by a concrete entry.
- `scheduled.ts`: intended-time weekday/DST gate, once-per-date shared ingestion, all-owner expiry, and enabled-user admission with summaries. Required injected transport; the production handler is separately gated by execution/schedule switches. One singleton `scheduled_pass` row consumes failed/interrupted scheduled passes; an attempt ID also fences freshly confirmed manual passes. Empty feeds reuse the latest matching nonempty current/working batch; without one, no generation is admitted and existing publications stay readable. No historical-feed source or retry/recovery service.
- `run-window.ts`: shared deadline/failed-launch SQL fence for effects, artifact writes, and publication; manual work also requires the admin role and unchanged base publication.
- `run-status.ts`: admin's own last successful publication/latest daily outcome, retained independently of generation cleanup; never an execution control.
- `summary-execution.ts`: featured-only source resolution, frozen per-user limits, durable no-repeat claims, atomic cache/outcome persistence, and terminal publication inputs.
- `../cloudflare-summary.ts`: shared environment-neutral single-attempt HTTP adapter with explicit credentials; hosted activation still requires Gateway/provider retry verification.

Local identity/fixture code lives under `scripts/`, never in this Worker's import graph. `tsconfig.json` checks this entry point, the internal execution/Workflow code, and the Workflow fixture with Workers types separately from the standalone Node application. `scripts/hosted-ranking-fixture.ts`, `scripts/hosted-summary-fixture.ts`, and `scripts/hosted-workflow-fixture.ts` are local test-only Workers with synthetic responses and recorded sources, never production execution endpoints. `scripts/hosted-production-fixture.ts` exercises real production adapters with recorded transport responses, never global fetch. Production retains the explicitly approved Workflow binding; local preview remains unbound. Tests use fixture bindings only. See `hosted-readiness.md` at repository root for the inactive deployment and separately approved activation checklist. CI uses ephemeral local D1 and requires no Cloudflare account or hosted database.
